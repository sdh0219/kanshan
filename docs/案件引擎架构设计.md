> 项目：看山探案录·灵魂共探（知乎黑客松 2026）
> 版本：v1.1（2026-08-25）
> 范围：案件引擎（案件生成 / 存储 / 探索流程 / 结局评估）全链路架构

## 一、系统定位

案件引擎是整个游戏的核心内容层，负责回答一个问题：**"玩家此刻能玩什么案子、案子怎么产生、玩的过程如何判定"**。它向上支撑三种探案入口（独立探索 / 组队共探 / 热榜生成），向下依赖知乎开放平台内容接口与直答 Agent API。

```
┌─────────────────────────────────────────────────────────┐

│   档案室页面    游戏工作台    我的卷宗    结果页              │
└───────────────────────────┬─────────────────────────────┘
                            │ REST API
┌───────────────────────────▼─────────────────────────────┐
```

## 二、案件数据模型

### 2.1 案件（CaseRecord）

存储于 `backend/data/cases.json`，是档案室展示与游戏引擎消费的唯一案件来源。

```typescript
interface CaseRecord {
  case_id: string;            // 'preset' | 'case_<timestamp>'
  case_title: string;         // 案件标题
  case_intro: string;         // 案情摘要（案件介绍页打字机文本）
  source: 'preset' | 'hotlist'; // 来源：官方预设 / 热榜AI生成
  source_topic?: string;      // 热榜生成时的原话题标题
  created_at: string;         // ISO 时间戳

  search_directions: {        // 搜证方向（4个左右）
    keyword: string;          // 玩家需要搜到的关键词
    hint: string;             // 看山给出的引导提示
    key_evidence: string;     // 命中后解锁的关键线索内容
    requires_dim: string;     // 关联的思维维度（微观/感性/广度/批判…）
  }[];

  npcs: {                     // 可讯问证人（3个左右）
    id: string;
    name: string;
    role: string;             // 身份角色（导师/同学/匿名者）
    identity: string;         // 人设prompt注入直答Agent
    knows: string;            // 知道的信息（编号列表）
    unknowns: string;         // 不知道的信息（防幻觉边界）
    personality: string;      // 性格说话风格
    trigger_rules: string[];  // 关键问题触发规则（API失败时兜底）
  }[];

  companion_exclusive_clues: { // 搭档专属线索（组队模式彩蛋）
    clue: string;
    requires_dim: string;
    trigger: string;
  }[];

  truth: string;              // 完整真相（结案后揭示）
  endings: {                  // 三档结局文本
    good: string;             // 关键证据达标
    neutral: string;          // 有线索但不足
    bad: string;              // 无关键证据
  };
  key_evidence_count: number; // 达成 good 结局所需关键证据数
}
```

**设计要点**：
- 案件是**自包含**的完整剧本——NPC人设、搜证方向、真相、结局全部内聚，游戏引擎无需任何外部剧本即可运行；
- `requires_dim` 把线索和思维指纹维度绑定，形成"你的思维类型决定你容易发现什么线索"的核心玩法；
- `trigger_rules` 兼作 API 容错降级文案，一份数据两用。

### 2.2 探索记录（ExploreRecord）

存储于 `backend/data/records.json`，按用户维度记录每一次结案。

```typescript
interface ExploreRecord {
  record_id: string;          // rec_<ts>_<rand>
  user_id: string;            // 知乎ID
  user_display_name: string;
  case_id: string;
  case_title: string;
  game_mode: 'solo' | 'team'; // 独立探索 / 组队共探
  companion_name?: string;    // 组队时的搭档名
  ending_type: 'good' | 'neutral' | 'bad';
  clue_count: number;         // 总线索数
  key_clue_count: number;     // 关键证据数
  companion_clue_count: number; // 搭档贡献线索数
  duration_seconds: number;   // 用时
  finished_at: string;        // 结案时间
}
```

**统计口径**（`computeStats` 纯函数，`npm test` 覆盖21个用例）：
- `total` = 记录总数；`good/neutral/bad` 三类之和恒等于 total；
- `solo/team` 之和恒等于 total；`total_clues` = Σ clue_count（缺省容错为0）。

## 三、案件来源：三条供给链

### 3.1 官方预设（preset）

`src/data/presetCase.ts` 内置"消失的学术新星"完整剧本。服务首次启动时由 `caseStore.loadCases()` 自动注入 cases.json（幂等，按 case_id 判重）。作为保底案件，保证**任何外部依赖失效时游戏仍完整可玩**。

### 3.2 热榜 AI 生成（hotlist）——主供给链

```
用户点"从热榜新建案件"
  → GET /api/archive/hot-topics
      → zhihuApi.getHotList()          （缓存30min + 限流重试）
      → 失败 → fallbackTopics 备用话题池（8个内置话题）
  → POST /api/archive/generate {hotTopicIndex}
      → caseGenerator.generateCaseFromTopic(topic)
          → caseGenPrompt 模板填充话题标题+摘要
          → agentApi.chatJSON()         （直答Agent产出案件JSON）
          → normalizeGeneratedCase()    （字段校验与补全）
      → caseStore.saveGeneratedCase()   （分配case_id、入库）
  → 档案室列表刷新，新案件可立即探索
```

**容错设计（三层）**：
1. **限流重试**：`zhihuApi.request()` 检测业务码 `Code=30001`，指数退避 1.5s/3s 重试2次；
2. **业务码感知缓存**：只有 `Code=0` 的成功响应才写入缓存——修复了旧版把限流空响应缓存10分钟的bug；
3. **备用话题池**：`fallbackTopics.ts` 内置8个探案友好的常青话题，热榜彻底不可用时无缝降级，前端显示"已切换备用话题池"提示。

### 3.3 normalizeGeneratedCase 字段防御

AI 生成的 JSON 不可全信，入库前统一补全：`case_title/case_intro` 缺省回退到话题原文，`npcs/search_directions` 缺省置空数组，`key_evidence_count` 缺省取 min(3, 方向数)。保证任何质量的生成结果都不会让游戏引擎崩溃。

## 四、探索流程引擎（gameEngine）

### 4.1 状态机

```
intro ──► search ──┬──► dialogue ──┐
  │                │              │（自由切换，无强制顺序）
  └────────────────┴──────────────┘
                 │
                 ▼
             reasoning（推理指认）
                 │
                 ▼
              ending（三档结局）
```

前端持有全部过程状态（clues / dialogues / currentNpc），后端**无会话状态**——每次请求由前端回传 `{state, caseId}`，后端从 caseStore 按 caseId 加载案件剧本。这样设计的好处：
- 后端天然水平扩展（无粘性会话）；
- 案件可热更新（cases.json 变更立即生效）；
- 探索中断零损失（刷新页面重新进入即可，线索在前端 store）。

### 4.2 搜证（searchForClues）

```
输入关键词 → zhihuApi.searchContent(keyword)    （真实知乎搜索，结果展示给玩家）
          → 方向匹配：directions.find(d => d.keyword.includes(kw) || kw.includes(d.keyword))
          → 命中且未收集过 → 生成 Clue{foundBy:'player', requiresDim}
          → 组队模式 → companion.action() 生成搭档观察（API失败返回兜底文案）
```

- **关键词包含匹配**：双向 includes，玩家输入"论文撤稿"即可命中预设方向"论文撤稿 学术不端"，降低猜词难度；
- 搜索失败（限流/网络）时 results 为空但**线索匹配逻辑照常执行**，游戏不被外部API阻塞。

### 4.3 讯问（talkToNpc）

```
选NPC + 自由提问
  → npcPromptTemplate 注入（人设/knows/unknowns/性格/触发规则）
  → agentApi.chat()                 （直答Agent实时生成NPC回复）
  → 失败 → 遍历 trigger_rules 找触发词 → 返回预设回复
        → 都不命中 → 返回该NPC的防御性默认台词
```

`knows/unknowns` 双列表是防幻觉关键：prompt 中明确告知NPC"你不知道什么"，避免AI证人说出剧本外的真相。

### 4.4 结局评估（evaluateEnding）

```typescript
keyClues = clues.filter(c => c.requiresDim).length
count >= case.key_evidence_count  → good
count >= 1                        → neutral
count == 0                        → bad
```

关键证据数与 `requires_dim` 绑定——只有搜到**正确方向**的线索才计入，乱搜普通关键词不解锁。阈值 `key_evidence_count` 按案件动态配置（AI生成案件方向数不足3时自动调低）。

### 4.5 模式分流（solo / team）

| 环节 | 独立探索 | 组队共探 |
|------|---------|---------|
| 搜证后 | 无搭档评论 | companion.action 生成搭档观察 |
| 讯问后 | 无 | 60%概率搭档插话（含专属线索彩蛋） |
| 指认前 | 无 | 搭档先发表推理总结 |
| 侧栏 | 显示玩家自己的档案 | 显示搭档档案卡 |

判定完全在前端 `gameMode` 字段分流，后端接口不变——同一套引擎服务两种模式。

## 五、数据流与持久化

```
cases.json   ──读取──►  archive/cases 列表 ──►  档案室卡片
             ──读取──►  game/case 详情   ──►  游戏工作台
             ──写入──►  archive/generate ──►  新案件入库

records.json ──写入──►  archive/record（结案自动上报）
             ──读取──►  archive/records?userId ──► 我的卷宗+统计
```

- **文件型存储**：黑客松演示场景下零部署依赖（无需数据库），直接读写 JSON；
- 读时全量载入内存、写时全量落盘——案件/记录量级（<1000）下性能无压力；
- 如需升级：`caseStore` 的6个函数（listCases/getCaseById/saveGeneratedCase/saveExploreRecord/getUserRecords/computeStats）是唯一数据访问面，替换为 SQLite/PostgreSQL 实现即可，路由层零改动。

| 方法 | 路径 | 职责 | 容错 |
|------|------|------|------|
| GET | /api/archive/cases | 案件列表（含统计字段） | — |

| POST | /api/game/talk | NPC对话（Agent生成） | 触发规则兜底 |
| POST | /api/game/evaluate | 结局判定 | — |

## 七、质量保障

- **类型检查**：前后端 `tsc --noEmit` 零错误；
- **统计测试**：`npm run test`（tests/stats.test.ts）——21个断言覆盖空记录、混合记录、非法值容错、用户隔离、数据清理5组场景；
- **端到端验证**：热榜生成案件全链路（生成→入库→搜证命中→结局评估）已实测通过；
- **浏览器实测**：首页→建档→档案室→组队→游戏→搜证→我的卷宗，8步截图验证无白屏无报错。

## 八、已知边界与演进方向

1. **文件存储并发写**：多实例部署需先迁移到数据库（见 §5）；
2. **生成质量依赖 Agent**：normalizeGeneratedCase 只做字段级防御，剧情逻辑质量依赖 caseGenPrompt 工程，可增加"生成后自动试玩校验"环节；
3. **热榜缓存30分钟**：演示场景够用；如需实时性可改为5分钟+ETag；
4. **记录无认证**：user_id 由前端声明，演示场景可接受；接入知乎OAuth后应以登录态为准；
5. **可玩性扩展**：搭档专属线索目前仅展示层彩蛋，可升级为"搭档发现的线索计入key_clue_count"让组队模式有真实数值收益。
