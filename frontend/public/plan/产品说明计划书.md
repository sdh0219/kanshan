## 一、项目概述

「看山探案录·灵魂共探」是一款基于知乎社区生态的 AI 侦探游戏。玩家输入知乎 ID，系统通过分析其回答内容构建五维「思维指纹」，据此生成互补型 AI 搭档，随后进入一起探案游戏——搜证、审讯 NPC、收集线索、推理指认，最终揭晓三档结局。

项目融合了知乎黑客松两大赛道：**灵魂匹配局**（基于思维指纹的社交匹配）与 **跨次元游乐场**（AI 驱动的互动叙事游戏），让知识社区的连接方式从「内容匹配」走向「认知互补协作」。

**一句话定位**：用知乎用户的思维指纹匹配互补型 AI 侦探搭档，在知乎热榜与搜索构建的案件世界中协作破案。

| 维度 | 说明 |
| --- | --- |
| 赛道 | 跨次元游乐场（跨赛道融合灵魂匹配局） |
| 类型 | 网页应用（React 前端 + Hono 后端，Cloudflare Workers 一体化托管） |
| 技术栈 | React 18 + Vite 5 + Tailwind CSS + Hono + TypeScript + Cloudflare KV |
| 交付形态 | 公网可访问的线上 Demo，评委可直接在浏览器中完整体验（免费层部署，无需信用卡） |

## 二、核心创作思路

### 2.1 问题洞察

知乎积累了大量来自真实问题的知识内容，但社区用户之间的连接仍主要停留在「关注」和「赞同」层面——**缺乏基于认知方式的深度匹配**。同时，知乎的盐言故事、热榜、搜索等内容生态天然具备悬疑叙事的土壤，却很少被用于游戏化场景。

我们观察到两个未被满足的需求：

- **认知层面的社交匹配**：现有社交产品匹配的是「兴趣」或「行为」，而非「思维方式」。一个偏重逻辑分析的人和另一个偏重感性共鸣的人，在知识社区中可能是绝佳的互补搭档。
- **内容生态的游戏化演绎**：知乎热榜话题每天都在产生新的社会故事，盐选故事有成熟的悬疑叙事，但它们只被「阅读」，从未被「玩」过。

### 2.2 解决方案

我们将两个需求合并为一个产品：**用思维指纹做社交匹配，用知乎内容做案件生成，用 AI 驱动探案过程。**

四大核心模块：

1. **思维指纹** — 搜索用户的知乎回答内容，由直答 Agent 分析为五维指纹（微观洞察 / 感性共鸣 / 广度涉猎 / 批判深度 / 逻辑思维），生成侦探能力档案。
2. **互补搭档** — 取指纹中最弱的两个维度，匹配互补型 AI 搭档模板，生成有独立人设、说话风格和专属线索的侦探伙伴。
3. **案件生成** — 从知乎热榜话题、盐言故事或用户投稿事件出发，由直答 Agent 生成自包含的完整案件剧本（NPC、搜证方向、真相、三档结局）。
4. **协作探案** — 玩家用关键词搜索知乎真实内容搜证，自由审讯 AI 驱动的 NPC，搭档在关键节点提供互补视角的观察与推理。

### 2.3 核心创新

**创新一：思维指纹有游戏价值。** 五维指纹不只是展示，直接映射探案能力——你的思维类型决定你容易发现什么线索。逻辑型玩家容易找到数据异常，感性型玩家容易察觉情感动机。

**创新二：个性化 AI 搭档。** 搭档不是通用助手，而是根据玩家思维弱点动态生成的互补角色。搭档的专属线索只有它能发现，组队模式有真实的协作收益。

**创新三：跨赛道融合。** 灵魂匹配局（社交）与跨次元游乐场（游戏）不是简单叠加——思维指纹同时驱动了社交匹配和游戏机制，形成「认识自己 → 找到搭档 → 一起破案」的完整体验闭环。

**创新四：知乎全生态深度整合。** 七类 API + 刘看山 IP 中，每一类都是游戏核心机制而非装饰——热榜生成案件、搜索驱动搜证、直答 Agent 驱动 NPC 与剧本生成、刘看山作为侦探向导贯穿全程。

### 2.4 双模式设计

为覆盖不同玩家需求，提供两种探案模式：

| 维度 | 独立探索 Solo | 组队共探 Team |
| --- | --- | --- |
| AI 搭档 | 无搭档，独立推理 | 生成互补型 AI 侦探搭档 |
| 搜证后 | 仅展示搜索结果 | 命中搭档互补维度的线索由搭档发现（金色标签），计入搭档贡献 |
| 审讯后 | 仅 NPC 回复 | 搭档插话点评，可触发搭档独占线索（同样计入关键证据与搭档贡献） |
| 指认前 | 直接进入推理 | 搭档先发表推理总结 |
| 侧栏 | 展示玩家自己的档案 | 展示搭档档案卡 |
| 难度 | 较高，纯靠自身思维 | 标准，有互补提示 |

> HTML 交互版本中此处有游戏流程状态机图，展示从案件介绍到搜证、审讯、推理、结局的完整流转关系。

## 三、产品功能架构

### 3.1 功能全景

产品由五个核心模块构成，覆盖从用户建档到案件探索到社交展示的完整闭环：

- **M1 思维指纹分析** — 输入知乎 ID → 搜索回答内容 → 直答 Agent 五维分析 → 雷达图 + 侦探能力档案
- **M2 AI 搭档生成** — 取最弱两维 → 匹配互补模板 → 直答 Agent 生成独立人设 → 自我介绍 + 说话风格 + 专属线索
- **M3 案件档案室** — 官方预设 + 热榜 AI 生成 + 盐言故事改编 + 用户投稿生成 → 案件列表 → 选案 → 模式选择 → 进入探案
- **M4 探案游戏引擎** — 搜证（知乎搜索 + 线索匹配）→ 审讯 NPC（Agent 实时对话）→ 推理指认 → 三档结局
- **M5 灵魂侦探榜** — 结案自动上报探索记录 → 按用户维度统计战绩 → 社区排行展示

### 3.2 案件来源：四条供给链

| 来源 | 标识 | 机制 | 容错 |
| --- | --- | --- | --- |
| 官方预设 | preset | 内置完整剧本「消失的学术新星」，代码内置不落库 | 任何外部依赖失效时游戏仍完整可玩 |
| 热榜生成 | case_* | 拉取知乎热榜 → 选话题 → 直答 Agent 生成案件 → 入库 | 智能重试 + 缓存 + 备用话题池 |
| 盐言故事改编 | case_* | 拉取黑客松专用故事接口（无需鉴权）→ 选故事 → AI 保留人物氛围重构为探案剧本 → 入库 | 接口失败时该入口提示暂不可用，其余来源不受影响 |
| 用户投稿 | custom_* | 用户输入事件描述 → 直答 Agent 改编为探案剧本 → 入库 | 输入校验（≥10字）+ 字段补全防御 |

## 四、技术实现方案

### 4.1 技术栈

| 层 | 技术 | 选型理由 |
| --- | --- | --- |
| 前端框架 | React 18 + Vite 5 | 组件化开发，Vite 秒级热更新，适合 48h 极限开发 |
| 样式方案 | Tailwind CSS + 自定义主题 | 原子化 CSS 快速迭代，暗黑悬疑主题定制 |
| 状态管理 | Zustand | 轻量全局状态，无需 Provider 包裹 |
| 图表方案 | 自研 SVG 雷达图组件 | 零依赖手绘五维雷达图，与暗黑主题像素级统一 |
| 后端框架 | Hono + TypeScript（Cloudflare Workers） | 轻量路由运行在边缘 Worker，前后端同构 TS，单域名托管无跨域 |
| 缓存 | 自研 lazy-TTL 进程内缓存 | 适配 Workers 运行时约束（禁全局定时器），API 限流场景零外部依赖 |
| 数据存储 | Cloudflare KV | 免费层每天 10 万次读 / 1000 次写，案件与记录量级远低于限额；天然持久化、免运维 |
| 外部 API | 知乎开放平台 7 类 + 刘看山 IP | 全量接入，每个 API 都是游戏核心机制 |

### 4.2 系统架构

系统整体部署为一个 Cloudflare Worker（单域名）：`/api/*` 请求进入 Hono 路由处理，其余路径由 Static Assets 直接返回 React 构建产物，生成案件与探案记录持久化在 KV。前端、后端、存储同域托管，无跨域、无独立服务器，免费层即可承载比赛访问量。

代码内部按职责分为：入口层（worker.ts 注册全部 API 路由，并在每个请求注入 KV 与环境绑定）、服务层（caseGenerator / caseStore / gameEngine / fingerprintService / companionService / zhihuApi / agentApi）、数据层（Cloudflare KV：kanshan:cases 案件库 + kanshan:records 探索记录）。

> **强烈建议查看 HTML 交互版本的系统架构图**，图中清晰展示了从页面到路由到服务到外部 API 的全链路调用关系。

### 4.3 核心引擎设计

**思维指纹分析（fingerprintService）**：用户输入知乎 ID → 调用知乎搜索 API 检索该用户的回答内容 → 提取标题和正文 → 注入指纹分析 Prompt → 直答 Agent 返回五维评分（每维含 score / toward / evidence）→ 生成侦探能力档案 → 缓存结果。

**AI 搭档生成（companionService）**：取指纹中评分最低的两个维度 → 按弱项匹配三种搭档模板（理性型 / 共情型 / 博学型）→ 注入搭档 Prompt → 直答 Agent 生成自我介绍文案 → API 失败时回退到模板预置文案。

**案件引擎（gameEngine + caseGenerator）**：案件引擎是无会话状态的——每次请求由前端回传 {state, caseId}，后端从 caseStore 加载案件剧本。这样设计的好处：后端天然水平扩展（无粘性会话）、案件可热更新（KV 写入立即生效）、探索中断零损失（刷新页面重新进入，线索在前端 store）。

**搜证逻辑（searchForClues）**：玩家输入关键词 → 调用知乎搜索 API 展示真实搜索结果 → 与案件预设的搜证方向做模糊语义匹配（token 包含 + 字符 2-gram 命中度，自然语言问句「张明的论文为什么被撤稿」也能命中「论文撤稿」方向）→ 命中且未收集过则生成线索对象 → 组队模式下，命中搭档互补维度的线索归因给搭档（线索墙「搭档发现」标签）并计入搭档贡献。搜索失败时结果为空但线索匹配照常执行，游戏不被外部 API 阻塞。

**NPC 审讯（talkToNpc）**：选 NPC + 自由提问 → 先将问题与该 NPC 的 trigger_rules 做 2-gram 相关性匹配，命中即返回精修预设台词（质量最高）→ 未命中则注入人设 Prompt（identity / knows / unknowns / personality / trigger_rules）由直答 Agent 实时生成回复 → 生成结果经台词修剪与跑题检测（与问题无词汇交集、或命中书面语标记即判定跑题），跑题或 API 失败均回退预设台词。knows / unknowns 双列表是防幻觉关键。

**结局评估（evaluateWithReasoning）**：双因子评估——关键证据数（带 requiresDim 标记的线索数）决定基础档位（达标 key_evidence_count 为 Good，≥1 为 Neutral，0 为 Bad）；玩家提交的结案陈词由直答 Agent 对照案件完整真相评分（0-10 分），≥8 分升一档、≤2 分降一档——推理精准可弥补证据不足，胡乱指认即使证据齐也会被打回。评分解析带容错（多字段名匹配 + 「8分/8/10」正则兜底），解析失败自动放弃 AI 评估、退回证据档位并使用通用点评，绝不把跑题内容展示给玩家。

### 4.4 数据流与持久化

数据持久化在 Cloudflare KV（键 kanshan:cases / kanshan:records），免费层额度对演示量级余量巨大，且天然持久、免运维。如需升级，caseStore 的 6 个异步函数是唯一数据访问面，替换为 D1 / 其他数据库即可，路由层零改动。

## 五、知乎生态深度契合

项目全量接入知乎开放平台七类 API 及刘看山 IP，每一类都是游戏核心机制而非装饰性集成：

| API | 游戏角色 | 契合度说明 |
| --- | --- | --- |
| 知乎热榜 | 案件生成源 | 热榜话题 → 直答 Agent 改编为探案剧本，让社区实时热点成为游戏内容引擎 |
| 知乎搜索 | 搜证机制 | 玩家输入关键词 → 真实知乎搜索结果展示给玩家，搜索是游戏核心交互 |
| 直答 Agent | 全流程 AI 引擎 | 驱动思维指纹分析、搭档生成、NPC 对话、案件剧本生成、推理评估——直答 Agent 是游戏的「大脑」 |
| 刘看山 IP | 侦探向导 | 刘看山作为侦探 NPC 贯穿全程，三视图 + 动态 GIF 用于头像、对话气泡、案件引导 |
| 知乎故事 | 案件改编源 | 黑客松专用盐言故事接口（免鉴权）→ AI 保留人物与氛围重构为探案剧本，让「读过的故事变成可以玩的案子」 |
| 知乎关注流 | 社交扩展 | 接口已接入封装，为「关注的人也在探案」社交玩法预留 |
| 全网搜索 | 搜证扩展 | 接口已接入封装，为知乎站外证据搜证预留 |
| 知乎知识 | 线索深化 | 接口已接入封装，为「搜证命中后提供知识卡片」预留 |

> 核心游戏闭环由前五项驱动（热榜、搜索、直答 Agent、刘看山 IP、故事）；关注流 / 全网搜索 / 知识三类接口已完成接入封装、能力就绪，作为产品演进路线上的预留扩展，避免做浅层堆砌。

**场景价值**：项目让知乎用户从「阅读者」变为「参与者」——你的知乎内容决定了你的侦探能力，热榜话题变成你的案件，搜索变成你的搜证工具，刘看山变成你的探案搭档。每一类 API 都在游戏中有不可替代的功能性角色。

## 六、API 配额与容错策略

### 6.1 配额管理

| API | 日配额 | 单局消耗 | 策略 |
| --- | --- | --- | --- |
| 直答 Agent | 100 次/天 | 6-8 次/局 | 3 个种子用户预缓存，约支持 12-15 局 |
| 知乎搜索 | 5000 次/天 | 3-5 次/局 | 充足，缓存 10 分钟 |
| 知乎热榜 | 100 次/天 | 1 次 | 缓存 30 分钟，仅 AI 动态案件使用 |

### 6.2 三层容错体系

外部 API 不可全信，系统设计了三层容错确保任何依赖失效时游戏仍可运行：

- **L1 智能重试** — 仅对服务端错误（5xx）做指数退避重试；限流（Code=30001）不重试——限流在秒级不会恢复，重试只会白白消耗当日配额
- **L2 业务码感知缓存** — 只有 Code=0 的成功响应才写入缓存，避免把限流空响应缓存导致后续全部命中脏数据
- **L3 多级降级兜底** — 热榜不可用 → 8 个备用话题池无缝降级；Agent 调用失败 → NPC trigger_rules 预设回复；搭档生成失败 → 模板预置文案；搜索失败 → 结果为空但线索匹配照常执行

### 6.3 AI 生成数据防御

直答 Agent 返回的 JSON 不可全信，normalizeGeneratedCase() 在入库前统一补全：case_title / case_intro 缺省回退到话题原文，npcs / search_directions 缺省置空数组，key_evidence_count 缺省取 min(3, 方向数)。保证任何质量的生成结果都不会让游戏引擎崩溃。

### 6.4 角色扮演台词三层防御

直答 Agent 是检索增强模型，天然倾向输出「知乎回答体」长文科普，且可能无视输出格式要求。为保证 NPC 与搭档在任何情况下都不「出戏」，台词链路设计了三层防御：

- **L1 Prompt 强约束** — 台词模板开头声明「这是角色扮演，你不是问答助手」，明确禁止科普/列条目/书面讲解腔，限定 1-3 句、60 字以内，并在 user 消息中二次强调
- **L2 台词硬修剪** — rolePlayTrim() 对 Agent 输出按句切分限量截取，剥除 Markdown 与列表痕迹，超长台词只保留前几句
- **L3 合格性自检回退** — 修剪后台词命中书面语标记（「根据」「综上」「一、」等）或与玩家问题无词汇交集即判定跑题，回退到精修预设台词；结构化输出（指纹五维、推理评分）做 schema 校验与容错提取，不合格直接使用预设数据——任何模型失控内容都不会到达玩家界面

### 7.1 视觉风格

## 九、演进规划

### 已识别的边界

- **KV 写并发**：KV 为最终一致，高频并发写场景需迁移到 D1 数据库（caseStore 6 函数是唯一数据访问面，替换零改动）
- **生成质量依赖 Agent**：normalizeGeneratedCase 只做字段级防御，可增加「生成后自动试玩校验」环节
- **记录无认证**：user_id 由前端声明，接入知乎 OAuth 后应以登录态为准

### 后续演进方向

- **接入知乎 OAuth** — 真实登录态替代手动输入 ID，登录人数作为人气奖评定依据
- **探案报告分享卡** — 一键生成含五维雷达图、结局印章与推理评分的分享图，打通知乎站内传播闭环（雷达图、印章、结局数据等素材均已在页面中就绪）
- **多人协作探案** — 从「人 + AI 搭档」扩展到「人 + 人 + AI」的真实多人协作模式
- **案件 UGC 社区** — 用户投稿案件可被其他玩家探索、评分，形成知乎社区内的探案 UGC 生态

**与知乎生态的长期价值**：项目的核心机制——思维指纹匹配 + 内容驱动案件生成——天然适配知乎知识社区。每一个知乎用户的回答内容都是指纹分析的数据源，每一个热榜话题都是案件素材，每一次搜索都是搜证行为。项目不是「在知乎上做个游戏」，而是「让知乎生态本身成为游戏」。
